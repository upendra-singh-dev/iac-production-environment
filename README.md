# Production environment — Terraform

VPC (public + private subnets, 2 AZs) · ECS Fargate service behind an
HTTPS-only ALB · PostgreSQL RDS in private subnets · S3 assets bucket.
One `terraform apply` builds all of it.

    terraform validate   Success! The configuration is valid.
    terraform fmt        clean
    estimated cost       $95.71 / month against a $150 cap (enforced, see below)

## Layout

    versions.tf              provider pins + S3 backend (partial config)
    main.tf                  providers, cost model, module wiring, assets bucket
    variables.tf outputs.tf  the eight inputs a new environment needs
    modules/networking/      VPC, subnets, IGW, single NAT, routes, S3 endpoint
    modules/compute/         ECS cluster/task/service, ALB + listeners, IAM
    modules/database/        RDS, subnet group, security group, Secrets Manager

## What you must configure first

Four things exist outside this stack because they outlive any one environment:

1. **An AWS account and credentials** with permission to create VPC, ECS, RDS,
   ELB, IAM, S3 and Secrets Manager resources.
2. **The remote state backend** — one-off, before the first `init`:

        aws s3api create-bucket --bucket tf-state-<account-id> \
          --region eu-west-1 --create-bucket-configuration LocationConstraint=eu-west-1
        aws s3api put-bucket-versioning --bucket tf-state-<account-id> \
          --versioning-configuration Status=Enabled
        aws s3api put-public-access-block --bucket tf-state-<account-id> \
          --public-access-block-configuration \
          BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
        aws dynamodb create-table --table-name tf-state-lock \
          --attribute-definitions AttributeName=LockID,AttributeType=S \
          --key-schema AttributeName=LockID,KeyType=HASH \
          --billing-mode PAY_PER_REQUEST --region eu-west-1

   Versioning matters: it is the only way back from a corrupted state file.
3. **An ACM certificate** in the same region covering `domain_name`, validated.
   Certificates outlive environments and their DNS validation is a one-off, so
   the ARN is an input rather than a managed resource.
4. **A container image in ECR**, built for **linux/arm64** (the task runs on
   Graviton) and containing a user with uid 10001 — the task definition refuses
   to run as root.

## Running it

    git clone https://github.com/upendra-singh-dev/iac-production-environment
    cd iac-production-environment
    cp terraform.tfvars.example terraform.tfvars   # then edit it

    terraform init -backend-config="bucket=tf-state-<account-id>" \
                   -backend-config="region=eu-west-1"
    terraform plan -out=tfplan
    terraform apply tfplan
    terraform destroy        # when the environment is finished with

Point `domain_name` at the `alb_dns_name` output (ALIAS in Route 53, or CNAME)
once the apply completes. `terraform output url` is the address.

There is no password anywhere in this repo or in `terraform.tfvars`. The
database credential is generated by `random_password`, written to Secrets
Manager, and injected into the container by the ECS agent at start.

## The $150 cap, and what it bought

Costs are computed in `main.tf` from the same values that configure the
resources, so changing an instance class moves the estimate in the same commit.
A `check` block fails the plan if the total exceeds `monthly_budget_usd`.

| Line                                   | $/month |
|----------------------------------------|--------:|
| ALB (730 h + 1 LCU)                    |   22.27 |
| **NAT gateway (single)**               |   32.85 |
| Fargate (1 on-demand + 1 Spot, ARM64)  |   11.71 |
| RDS db.t4g.micro, single-AZ            |   11.68 |
| gp3 storage, 20 GB                     |    2.30 |
| Secrets, logs, egress, NAT data        |   14.90 |
| **Total**                              | **95.71** |

A conventional build breaches the cap on the database alone: db.t4g.medium
Multi-AZ is `0.128 x 2 x 730 = $186.88`.

### Three trade-offs, and what each one costs you

**1. RDS is single-AZ.** Multi-AZ on this instance class *does* fit — the model
puts it at $109.69 — so this is a judgement, not a hard constraint. The standby
would be the same undersized class and would address one of the three failure
modes below; the $14/month is held instead against the variable lines (egress,
LCU, NAT per-GB) that grow with traffic. Flip `db_multi_az = true` and the cost
model re-checks the cap for you.

> **Consequence.** If the AZ hosting RDS fails, expect **20–25 minutes of
> downtime**: 1–2 min to alarm, 10–15 min to restore a 20 GB db.t4g.micro from
> the latest automated snapshot into the surviving AZ, then ~5 min to update the
> Secrets Manager host and cycle the ECS tasks. **RPO is about 5 minutes**,
> because `backup_retention_period = 7` enables point-in-time recovery; without
> PITR it would be up to 24 hours. If the *instance* fails but the AZ survives,
> RDS replaces the host automatically in 3–6 minutes and no action is needed.

**2. One NAT gateway, not one per AZ.** A second is $32.85/month — a third of
the remaining budget for redundancy on a path that carries image pulls and
Secrets Manager calls, not user traffic.

> **Consequence.** If the AZ holding the NAT fails, private subnets in *both*
> AZs lose egress. Requests already being served keep working — the ALB reaches
> tasks inside the VPC — but image pulls, new deployments and scale-out fail
> until you move it. Recovery is `terraform apply` after changing the NAT's
> subnet: **3–5 minutes**. `terraform output egress_az` names the AZ at risk.

**3. Fargate Spot for all but one task.** Spot is ~70% cheaper; `ondemand_base
= 1` keeps one guaranteed task so a reclamation cannot take the service to zero,
and a variable validation refuses a value below 1.

> **Consequence.** During a Spot capacity crunch the service can drop to a
> single task for up to a few minutes. Expect higher latency under load, not an
> outage. Reclamation gives a 120-second SIGTERM warning, which is longer than
> the 30-second deregistration delay, so in-flight requests drain cleanly.

## Security posture

- The ECS task runs as **uid 10001** with a read-only root filesystem and all
  Linux capabilities dropped.
- Two IAM roles, both written by hand. The AWS-managed
  `AmazonECSTaskExecutionRolePolicy` is deliberately **not** attached: it grants
  ECR and CloudWatch actions on `*`. The execution role can pull one repository,
  write one log group and read one secret. The task role can reach one bucket
  and has no Secrets Manager access at all, so a compromised process cannot
  re-read the database credential the agent injected.
- RDS is `publicly_accessible = false`, in private subnets, reachable only from
  the task security group — by security-group reference, not a CIDR.
- The ALB terminates TLS 1.3 and redirects :80 to :443.

## Known gaps

- Task egress is `0.0.0.0/0`. Narrowing to prefix lists and interface endpoints
  is the next hardening step; it is not done here.
- No autoscaling policy. `desired_count` is fixed at 2.
- No WAF on the ALB (~$8/month plus per-request) and no VPC flow logs.
- `terraform apply` has not been run against a live account: this environment
  has no AWS credentials. `validate` and `fmt` pass and the plan graph resolves.
